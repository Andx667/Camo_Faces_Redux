**2026-09-11 update 5 — actual root cause found: leading backslash in embedded p3d texture/material paths.** Update 4's binarization theory was disproven by testing: `hemtt launch -b` (binarize on, file-patching off) still showed the same failures. Went back to basics on user's suggestion — checked a real, BI-documented precedent: the wiki for `createSimpleObject` states that before Arma 3 ~2.07, a p3d path could not start with a leading backslash or the engine wouldn't resolve it. Byte-scanning confirmed every single texture/material string in all three p3d files, in both LODs, starts with a literal `\` (`\z\cfr\addons\items\data\tex\...`) — the CfgWeapons `model=` reference has the same leading backslash (via CBA's `PATHTOF` macro) but that one works fine, because config text goes through rapification, which likely normalizes it; the raw strings baked directly into the p3d's face records are used completely literally at runtime.

**Fix applied and verified:** scripted a full LOD rebuild (not a same-length patch, since removing a byte shifts everything after it — verified safe first, since MLOD's outer header only stores a LOD count, no absolute offset table) that strips the leading `\` from every texture/material string in both LODs of all three files. Verified byte-for-byte against the originals first: vertex data, normals, face point/normal indices, flags, and both LODs' trailing selection-tag (`TAGG`) sections are all identical — only the leading backslash is gone from each path. Applied to all three:
- `BW_Facepaint.p3d`: 896 strings fixed (105,730 → 104,834 bytes)
- `US_Facepaint.p3d`: 4,832 strings fixed (561,511 → 556,679 bytes — note: this file had grown to 573,591 bytes at some point outside this session's tracked edits, likely an Object Builder resave; offsets were re-derived fresh from disk, not assumed)
- `SERBIAN_Facepaint.p3d`: 4,832 strings fixed (573,591 → 568,759 bytes; still pointing at `us_facepaint.rvmat`/`us_facepaint_co.paa` per the deferred item above — this fix doesn't change that, just removes the leading backslash from whatever path each face currently has)

**Confirmed in-game 2026-09-11:** after also applying the same leading-backslash fix to `BW_Facepaint.rvmat`/`US_Facepaint.rvmat`'s own `Stage1`/`Stage5` texture paths (the p3d fix alone got the diffuse texture and material loading working, but the rvmat's own internal normal/spec map references still had the same bug), every `Cannot load texture`/`Cannot load material file` warning is gone. Live spot-tested via the actual camo-apply flow (see `addons/dialog` fixes, tracked in conversation not here) — renders correctly.

**2026-09-11 update 4 — likely the real root cause of the in-game "white, no texture" symptom (superseded by update 5 above, kept for the record):** In-game testing (via the `.hemttout/dev` build) showed `Cannot load texture`/`Cannot load material file` warnings for **all three** items, including `US_Facepaint.p3d`, which byte-scanning proved has zero case issues anywhere in the file. That ruled out case mismatch as the (sole) explanation. Root cause found: `hemtt dev` (used for all testing so far — that's why the build lives at `.hemttout/dev`) intentionally ships **raw MLOD** p3d files (Object Builder's editable/source format — confirmed via byte-scan, packed p3d starts with the `MLOD` signature) instead of binarized `ODOL` format, by design, for fast iteration. The real game client can display MLOD geometry (hence "white, no texture" — geometry renders, material/texture references don't reliably resolve) but this is not how a real build ships. Ran `hemtt build` (not `hemtt dev`) — it successfully binarized all three p3d files to real `ODOL` format (`BW_Facepaint.p3d` 105,730 → 27,305 bytes; confirmed via byte-scan of the resulting `.hemttout/build/addons/cfr_items.pbo`). **Next step: point the Arma 3 launcher at `.hemttout/build` instead of `.hemttout/dev` and retest** — if this was the root cause, all three items should render correctly now, independent of the case/UV fixes above (which are still real, correct fixes, just not what was causing this particular in-game symptom).

**2026-09-10 update 3:** User opened all three items in Object Builder/VS Code preview — all three show a 2nd LOD named "Unknown 100001", but it only renders broken on BW. Re-scanned LOD boundaries on all three files to confirm why: US and SERBIAN's LOD 1 both carry real (if occasionally wrong) material/texture strings, so the "Unknown 100001" tag is just this mod's own convention for LOD 1 and is **not** the bug. BW's LOD 1 is the only one with zero texture/material strings at all. This **reverses last update's "maybe it's a shadow LOD, not a bug" theory** — Issue #4 is confirmed a real, simple bug: BW's LOD 1 is just missing the assignment that US/Serbian's LOD 1 already has correctly.
